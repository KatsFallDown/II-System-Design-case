# ML и LLM

## Разделение задач

| Задача | Подход | Почему |
|---|---|---|
| Валидация, sensitive topics, финальная policy | Правила | Требуются предсказуемость, аудит и запрет обхода safety-политики |
| Категория тикета | TF-IDF + Logistic Regression | Быстрый интерпретируемый baseline для размеченных классов |
| Операционный риск в PoC | TF-IDF + Logistic Regression по `priority` | Позволяет проверить pipeline, но `priority` является только proxy |
| Похожие случаи | TF-IDF + cosine similarity | Не требует внешней модели и работает локально |
| Достаточность информации и текст ответа | LLM | Требуется работа с контекстом и формирование естественного языка |
| Финальное действие | Не LLM | Цена ошибки зависит от бизнес-policy, а не от правдоподобия текста |

## Текущие модели и данные

Обе классификационные модели обучаются внутри проекта на английской части Customer Support Tickets: 11 923 записи, текст `subject + body`. Category label берётся из `queue`; risk proxy — из `priority` (`low`, `medium`, `high`). Используется split 80/20, `random_state=42`, stratification и `class_weight="balanced"`. Артефакты сохраняются joblib и повторно используются.

Текущий baseline:

| Модель | Accuracy | Macro-F1 |
|---|---:|---:|
| Category | 0.438 | 0.422 |
| Risk proxy | 0.562 | 0.549 |

Эти значения достаточны только для демонстрации orchestration. До пилота нужны confusion matrix по каждому классу, recall для high-risk, calibration error/Brier score, coverage при заданном confidence и стоимость ошибок по бизнес-сценариям. Accuracy нельзя использовать как единственный критерий из-за дисбаланса классов и разной цены ошибок.

LLM — открытая Qwen3.5-4B-Q8 GGUF, запускаемая локальным llama.cpp; обязательный mock остаётся детерминированным baseline. LLM получает только текущий запрос, историю, предсказания и несколько найденных примеров. Ответ валидируется Pydantic; скрытые рассуждения не сохраняются.

## Retrieval и embeddings

TF-IDF retrieval — первый baseline: top-20 кандидатов, до пяти примеров выше configurable similarity threshold. Его качество проверяется Recall@K/MRR на парах «новый тикет — действительно полезный исторический случай» и ручной оценкой релевантности/безопасности ответа.

Embeddings уместны после фиксации baseline, если TF-IDF плохо находит семантически близкие перефразировки. Тогда выбирается открытая локальная multilingual/English embedding-модель по Recall@K, latency, размеру индекса и стабильности на доменных данных. Reranker добавляется только при доказанном выигрыше, а не по умолчанию.

## Где LLM не используется

LLM не определяет high-risk override, пороги, allowlist, финальное действие и право автоматического закрытия. Ей также нельзя доверять факты об аккаунте, возврате средств, SLA или внутренних процедурах, которых нет в переданном утверждённом контексте. При отсутствии надёжного контекста LLM должна запросить данные или подготовить эскалацию.

## Валидация и низкая уверенность

Offline validation должна быть временным holdout, а не только случайным split, чтобы измерить domain shift. Перед включением auto-reply проводится shadow mode: решение сравнивается с категорией, ответом и эскалацией оператора без отправки пользователю. Затем запускается ограниченный пилот по allowlist с guardrail-метриками CSAT, reopen rate и ошибочными auto-reply.

Низкая confidence категории/риска, низкая retrieval similarity, конфликт rule/model или ошибка LLM запрещают auto-reply. Если известны конкретные недостающие поля — `ASK_CLARIFICATION`; если проблема неоднозначна или рискованна — `ESCALATE`.

## Разметка production risk

Для production нужна отдельная разметка риска, потому что `priority` описывает срочность, а не стоимость ошибочной автоматизации. Размечается репрезентативная выборка с участием support, security, legal и product: допустимость auto-reply, обязательность оператора, тип потенциального ущерба и стоимость false negative/false positive. Неоднозначные примеры проходят двойную разметку и adjudication; guideline и agreement версионируются вместе с моделью.
